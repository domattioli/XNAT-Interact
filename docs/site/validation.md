# Stress-testing against a live XNAT server found and fixed three release-blocking defects the offline suite could not see

This page documents a validation campaign run on 2026-06-12 against a real XNAT 1.9.3 server (the same platform family as the UIowa RPACS deployment), booted in an isolated container from `tests/integration/xnat_local/`. Every claim below carries its measurement; raw logs and per-lane JSON live under `tests/stress/results/` and `docs/STRESS_TEST_PLAN.md` in the repository.

No UIowa VPN, no production server, and no patient data were involved: the server URL is overridden by the `XNAT_SERVER_URL` environment variable, and all images are synthetic fluoroscopy frames generated by a seeded factory (collimation field, bone-like structures, guide-wires — visually plausible, content-hash distinct, zero PHI).

![Synthetic fluoroscopy frames](assets/synthetic_frames.png)

## The offline suite was green while the production login was unusable

Before the campaign, the offline test suite passed 1154 tests with 0 failures. Against a live server, the very first interactive step failed: the production login factory imported a function (`build_server`) that did not exist, so every real login attempt died with an ImportError that the error handler re-labeled "Cannot reach the XNAT server — check your VPN." Test-double injection had kept 100% of app-logic tests green around a login that could never succeed in production. The objective signal (a live round-trip) disagreed with the subjective one (a green suite), and the live signal was right.

Two further defects of the same fake-green class surfaced within the first hour:

| Defect | Offline suite | Live server |
|---|---|---|
| Production login (`build_server` missing) | green | every login fails, mislabeled as VPN error |
| Upload session typing (`create(xsiType=…)`) | green | kwarg silently ignored; sessions stored as `xnat:mrSessionData`, invisible to the tool's own `rfSessionData` queries |
| Whole-surgery download (scan addressed by its *type* string) | green | 0 of 3 staged files retrieved |

All three are fixed on this branch, each with a regression test derived from the live failure. The suite now passes 1276 tests, and the fixes were re-verified against the live server before merging.

## Round-trip integrity is measured, not assumed

The volume lane published 10 complete synthetic surgeries (20 frames each) through the unmodified `SourceRFSession.publish_to_xnat` pipeline — de-identification gate included — at a mean of 1.71 s per surgery (min 1.44, max 2.91), with zero empty subject/experiment/scan shells left on the server (the issue #32 invariant). The download leg then retrieved 206 files through `app/logic` browse + download, and the raw `PixelData` SHA-256 of every retrieved frame matched its uploaded source exactly: **20 of 20 hashes identical**, with `PatientName`/`PatientID` confirmed redacted in every downloaded file. Lane results are committed as JSON under `tests/stress/results/`.

Getting that round trip to work surfaced four more fake-green defects (real pyxnat has no `list_files()`; `resources().get()` returns numeric IDs that read back silently empty; pyxnat's `put_zip` PUTs to a numeric resource path that 404s under rf-typed sessions; assessor file operations 404 when label-addressed) — each now fixed with a regression test that models the real server's shape instead of the test double's.

## Stress lanes: what held and what didn't

| Lane | Result |
|---|---|
| Volume (10 × 20 frames) | 10/10 published, no shells, 1.71 s mean |
| Oversized case (1,005 frames) | accepted after the ≥1000-instance filename fix; previously a hard `AssertionError` |
| Malformed inputs (truncated, non-DICOM, RGB) | rejected client-side with a FriendlyError naming the offending files — originally raw internal asserts |
| Concurrency (4 parallel workers) | duplicate-config pushes produced raw `DatabaseError`/`AssertionError` with **zero** `LostUpdateError` — the lost-update guard does not catch real interleaving (open finding) |
| Duplicate re-upload (exact/subset/superset/partial) | initially **all accepted** — the dedup engine was dead-wired (production never passed `dedup_registry` to `publish_to_xnat`) and its hash comparison mixed lower/uppercase so intersections were always empty. Now wired and re-verified live: all four overlap classes rejected with an evidence package, disjoint accepted |

The duplicate-detection hash itself was characterized across 200 transform pairs as the regression baseline for the issue #32 redesign: its claimed brightness invariance held in 1 of 40 cases and its scale invariance in 0 of 20 — in practice an exact-content hash with extra steps. Full table: `tests/stress/results/hash_characterization.json`.

## Platform behaviors future deployments must know about

Isolated on stock XNAT 1.9.3 with reproduction steps in the issue tracker:

1. **Assessor files 404 when addressed by label**; the identical operation addressed by the assessor's accession ID returns 200. The gateway now resolves label → accession ID before every assessor file operation (GAP-001).
2. **`rfSessionData` sessions are absent from project- and subject-scoped listings** unless the server carries display configuration for that type — while remaining fully addressable by direct path and visible in `/data/experiments?project=`. The browse layer now falls back to the global listing (GAP-002).
3. **File PUTs against numeric resource IDs 404 under rf-typed sessions** while label-addressed PUTs succeed — this breaks pyxnat's own `put_zip`; the gateway now issues label-addressed REST PUTs (GAP-003).

Note: the production query path also references `xnat:esvSessionData`, which is not part of the stock XNAT schema at all; arthroscopy listings therefore depend on a server-side type definition that only the UIowa deployment can confirm. This and the historical `mrSessionData` typing of pre-fix uploads are tracked in issue #39.
